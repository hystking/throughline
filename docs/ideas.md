## 💡 A. トレンド機能 — 「直近の話題」の流れを追える (優先度: 高)

> 2026-08-03 gon 発案。クラスタリングの議論から派生。

### やりたいこと

日次ダイジェストは「その日に何があったか」しか見せられない。
**キーワードを軸に、そのトピックが数日〜数週間でどう動いたかを追える**ようにしたい。

例:「推論コスト」というキーワードを選ぶと、
7/28 A社が値下げ → 7/31 B社が対抗 → 8/2 ベンチマーク記事 …
という時系列が 1 ページで読める。

### なぜ自然に実装できるか

必要なデータは **すでに v1 で取れている**。

- `article.tags[]` — 記事ごとのキーワード (3〜5個)
- `article.category`
- `digest.themes[]` — Synthesize が抽出した「その日の潮流」
- `digest.article_order` / `clusters` — 同一トピックの統合情報

つまり **Publish ステージに集計とページ生成を足すだけ**で成立する。
新しい LLM 呼び出しも、新しい収集処理も要らない。

### 実装スケッチ

```
s3://data/state/trends.json
  {
    "topics": {
      "<slug>": {
        "label": "推論コスト",
        "aliases": ["inference cost", "推論単価", "API 値下げ"],
        "articles": [
          {"date": "2026-07-28", "article_id": "a1b2c3", "title_ja": "...", "importance": 4},
          {"date": "2026-07-31", "article_id": "d4e5f6", "title_ja": "...", "importance": 5}
        ],
        "daily_counts": {"2026-07-28": 1, "2026-07-31": 2, "2026-08-02": 1},
        "first_seen": "2026-07-28",
        "last_seen": "2026-08-02"
      }
    }
  }
```

生成するページ (いずれも静的・JS 不要):

| パス | 内容 |
|---|---|
| `/trends/` | 直近 30 日で**伸びている**キーワード上位 20。スパークラインは Unicode ブロック文字 (`▁▂▃▅▇`) で描けば画像も SVG も不要 |
| `/topic/<slug>/` | そのキーワードの記事を**時系列で縦に並べる**。これが「流れを追う」本体 |
| 日別ページ | 各記事カードのタグをリンク化 → `/topic/<slug>/` へ飛ばす |

「伸びている」の定義 (案):
```
momentum = (直近 7 日の出現数 + 1) / (その前 21 日の出現数 / 3 + 1)
```
出現数だけだと定番語 (`LLM` 等) が上位を占めるため、比率で見る。
`importance` の合計で重み付けするとなお良い。

### 難所

1. **タグの表記ゆれ** — `LLM` / `大規模言語モデル` / `Large Language Model` が別トピックになってしまう。対策案:
   - (a) 正規化辞書を `config/topics.yaml` に持つ。手で育てる。確実だが手間
   - (b) 週次で「タグ統合」の LLM コールを 1 回走らせ、エイリアスを自動生成する
   - (c) 埋め込みでクラスタリング。最も自動的だが依存が増える
   → **(a) で始めて (b) を足す**のが現実的。
2. **Research エージェントにタグを安定して出させる** — 現状の schema は自由記述。
   `config/topics.yaml` の既知タグ一覧をプロンプトに渡し「該当すれば既存タグを優先、なければ新規」と指示するのが良さそう。
3. **既存記事の遡及タグ付け** — 過去分にトレンドを効かせたいなら、蓄積後に一度バッチで振り直す必要がある。運用開始時から入れておくのが楽。

### 派生: 「続報」リンク

同じ仕組みで、記事カードに **「このトピックの前回: 7/28 ○○」** を出せる。
クラスタリングで 1 枚にまとめた記事の *日をまたいだ版* に相当する。
トレンド機能より先に、こちらだけ入れる手もある (実装が軽い)。

## B. X / Twitter の取り込み (優先度: 中)

前身 Skill では `bird` CLI で "Tech Officials" リスト (id: `2016572435089526970`) を取得していたが、
Lambda 上では同等の手段がない。X API は有料。v1 では除外した。

選択肢:
- X API Basic ($100/月〜) を契約する。コストが API 課金に上乗せされる
- Nitter 系インスタンス → 不安定。運用に耐えない
- 自宅/EC2 に `bird` を置き、収集結果だけを S3 に置く小さなジョブを別途走らせる →
  Collect が S3 から読むだけで済むので、パイプライン本体は無改造。**これが一番筋が良さそう**

## C. 週次まとめ (優先度: 中)

日曜に直近 7 日の `digest.json` を集めて「今週の 5 本」を生成し `/weekly/<YYYY-Www>/` に出す。
- Synthesize と同型の処理なので実装は軽い
- トレンド機能 (A) が入っていれば「今週伸びた話題」も自動で書ける
- EventBridge のルールを 1 本足すだけ

---

## D. Discord / Slack へのシンク (優先度: 中)

前身の配信先。Publish ステージにアダプタを足すだけで対応できる設計にしてある。
- 1 記事 = 1 投稿 (前身の仕様)
- サイトの URL を添えるだけの簡易版でも十分かもしれない

---

## E. Webhook ベースの非同期化 (優先度: 低 / 効いてくるのは規模が増えたとき)

現状は Research Lambda が SSE ストリームを**待つ**ため、Lambda の 15 分上限に縛られている。
Managed Agents の Webhook (`session.status_idled` / `session.status_terminated`) を
API Gateway → Lambda で受ければ、待たなくて済む。

- 必要なもの: API Gateway + HMAC 署名検証 + セッション状態を持つ DynamoDB
- 見返り: 記事数を増やしても時間制約に当たらない。1 記事に 30 分かけることも可能
- v1 の規模 (12 本 × 数分) では過剰

---

## F. 独自ドメイン (優先度: 低)

Route53 + ACM (us-east-1) + CloudFront alias。やること自体は定型。
今は CloudFront ドメイン直出しで運用する方針。

---

## G. Managed Agents の Scheduled Deployments への移行 (優先度: 低 / たぶんやらない)

EventBridge + Step Functions を使わず、Anthropic 側の cron でセッションを起こす構成。
ただし S3 への書き出しをエージェントにやらせる = AWS 認証情報をサンドボックスに渡すことになり、
プロンプトインジェクションの被害範囲が広がる。**現構成のほうが安全**。

---

## H. 細かいもの

- 記事カードに**読了目安時間**を出す (summary の文字数から機械的に算出)
- `confidence: low` の記事に注記を出す (schema には既にある。表示するかは `config/pipeline.yaml` の `site.show_confidence_badge`)
- OGP 画像の自動生成 — 画像生成は JS 不要でも Lambda 側にフォント依存が増える。優先度低
- 過去記事の全文検索 — 静的サイトでやるなら Pagefind 等。ただし JS が必要になるので方針と衝突する
- `/category/<name>/` ページ — トレンド機能 (A) の副産物として自然に作れる
- 収集した candidates のうち**採用されなかったもの**も `/dropped/<date>/` に出す (取りこぼしの検証用、noindex)
